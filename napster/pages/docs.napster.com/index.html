Quick start

NIM's sandbox answers the 2001 protocol, serves the pages the client loads, carries chat, and presents a local music collection as search results, so an original client can be used the way it was used at the time.

The client is yours to supply and NIM never installs one. Where it goes depends on how you run it, and that is what a mode sets: a Wine prefix on this machine, or Windows in a VM. Each mode is installed and run on its own:

nim-byo A client you installed yourself, in your own Wine prefix. Configures it in place and starts it. Redirects the client; does not confine it.
nim-mode-byo-wine
 
nim-vm A client in a Windows VM, or on real hardware. Writes a .reg to apply in the guest. With a host-only adapter the guest's only route anywhere is this machine, which is the stronger seal of the two.
nim-mode-vm-guest
 

Install a mode, run it, and it prints what to do next:

uv tool install --find-links nim/dist ./nim/modes/byo-wine
nim-byo                       # uses $WINEPREFIX
nim-byo --prefix ~/.wine-napster --nick preserve

uv tool install --find-links nim/dist ./nim/modes/vm-guest
nim-vm --host 192.168.56.1    # with no --host it lists candidates

The --find-links is only needed until the sandbox itself is published: it tells uv where to find the library a mode depends on, built by uv build in nim/library. Removing a mode is uv tool uninstall nim-mode-byo-wine.

Where the client goes. For nim-byo, install it into a Wine prefix with its own installer (WINEPREFIX=~/.local/share/nim/wineprefix wine setup.exe) and the mode finds napster.exe inside that prefix by itself; --prefix points at another one. For nim-vm, install it inside the guest as you would any Windows program -- nothing on this side needs a copy. The Help tab has both in full.

The account matters. The client stores its proxy settings per account, under HKLM\Software\Napster\<nick>, so sign in as the nick the mode configured. Signing in as anyone else dials server.napster.com and fails.

Nothing needs name resolution. The proxy routes by destination port and ignores the address, because the address the client asks for is its own failed resolution of a hostname compiled into the binary. So no hosts file, no resolver, and no namespace is required just to point a client here.

The sandbox alone, with no mode around it, is napster-sandbox. It needs no checkout either: the exhibit manifests ship inside the package.

napster-sandbox --socks            # and point a client at it
nim-client configure --prefix ~/.wine --nick preserve
nim-client emit --nick preserve --host 192.168.56.1 -o nim.reg


Usage

NIM is a Python library with a server built on it. Every part of the server has a working default, so this runs:

from napster import Deployment, serve

serve(Deployment())

The sandbox serves a real directory as search results:

from napster import Deployment, serve
from napster.providers.collection import LocalCollection

library = LocalCollection('~/Music', seed='nim')
library.index()

serve(Deployment(library=library))

The fields are the capability domains. Each one is a typing.Protocol, so anything with the right methods will do.

    presence: Any = field(default_factory=SessionRegistryPresence)
    chat: Any = field(default_factory=InternalChat)

    rendezvous: Any = field(default_factory=DirectRendezvous)
    policy: Any = field(default_factory=DefaultPolicy)
    web: Any = None
    mail: Any = None
    federation: Any = None

    # Surfaces the client reaches that are not the protocol itself.
    metaserver_targets: tuple[str, ...] = ()


The client

NIM does not ship a Napster client and does not link to one. You supply the binary, and the Help tab says where to put it.

Three things have to be true before it works: it has to reach the server, its browser has to reach the pages, and a link it opens must not escape to the host.

It reaches the server through its own proxy setting, which carries the control connection and not only transfers. The proxy routes by destination port and ignores the address, so no name resolution is involved:

HKLM\Software\Napster\<nick>
    ProxyServer  = 127.0.0.1
    ProxyPort    = 1080
    ProxyVersion = 5

nim-client writes those into a Wine prefix, or emits them as a .reg for a client in a VM. nim-client show --nick <nick> prints them and writes nothing.

First contact is not the server port. The client asks a metaserver on 8875 where to go, and the server speaks first:

napster.metaserver . Metaserver.handle
async def handle(self, reader: asyncio.StreamReader,
                 writer: asyncio.StreamWriter) -> None:
    try:
        # The client's first connection of all. In the era a name lookup
        # sat in front of this.
        await self.latency.pause("metaserver")
        writer.write(f"{next(self._cycle)}\n".encode("latin1"))
        await writer.drain()
    except ConnectionError:
        pass
    finally:
        writer.close()

It reaches the pages through a second setting, because the embedded browser honours WinINet rather than the client's own proxy. The sealed museum mode maps names instead, inside its namespace:

napster.web . hosts_line
def hosts_line(ip: str = "127.0.0.1", *, include_forwarded: bool = True) -> str:
    extra = ("server.napster.com", "server2.napster.com", "upgrade.napster.com",
             "download.napster.com", "mail.napster.com")
    names = [*MUSEUM_HOSTS, *extra]
    if include_forwarded:
        try:
            from .communities import forwarded_hosts
            names += [h for h in forwarded_hosts() if h not in names]
        except Exception:
            pass
    return f"{ip}\tlocalhost " + " ".join(names)

The link is the one that is easy to miss. A click calls ShellExecute, and Wine hands the url to a program outside the prefix, on the real network. The handler is pointed at the prefix's own browser, which reaches only what the sandbox serves. nim-client configure sets that too.



The pages

The client's Home tab loads a web page over plain HTTP on port 80. The browser is the Windows one, not the client's own socket layer, so it ignores the SOCKS proxy and goes by name. NIM serves those names itself.

Pages are mounted per host rather than per path. Archived pages use relative urls, so a snapshot served under a subdirectory looks for its images in the wrong place, while the same snapshot on its own hostname works untouched.

napster.web . museum
def museum(exhibits_dir: str | Path, *, landing: str = "nim-default",
           cache_dir=None, log=None) -> ExhibitServer:

NIM's own pages are files on disk. The 2000 snapshot is not: nothing archived is stored in this project. It is fetched from the Internet Archive when something asks for it, then cached outside the repository. The id_ and im_ modifiers return the original bytes, with no archive toolbar wrapped around them:

napster.web . ForwardExhibit.upstream_url
def upstream_url(self, host: str, path: str, *, index: bool = True) -> str:
    host = self.archived_host(host)
    rel = urllib.parse.urlparse(path).path or "/"
    directory = rel.endswith("/")
    if directory and index:
        rel += "index.html"
    suffix = Path(rel).suffix.lower()
    # A bare directory url has no suffix but is a page, so it needs the
    # text modifier. Without this it is fetched as if it were an image and
    # the archive's toolbar comes back embedded in the html.
    modifier = (self.text_mod
                if directory or suffix in _TEXT_SUFFIXES
                else self.binary_mod)
    return self.template.format(
        snapshot=self.snapshot, modifier=modifier,
        url=f"http://{host}{rel}")

The CDNOW button in the top right of the client is wired through the same machinery. The binary holds the menu text but no url at all. Driving the live client under a logging proxy showed it requests shop.napster.com, which in 2001 answered a redirect to a co-branded CDNOW page. NIM answers the same redirect, and forwards what it points at:

napster.web . RedirectExhibit.redirect_for
def redirect_for(self, host: str, path: str) -> str | None:
    return self.target

So the button resolves, and the page it lands on is the archived one from February 2001.



Chat adapters

Chat is a replaceable part. The default keeps messages inside NIM. An adapter can put them somewhere else instead, and IRC is the worked example rather than the only option.

An adapter implements this. Nothing in it is IRC-specific, which is the point:

napster.providers . ChatTarget
@runtime_checkable
class ChatTarget(Protocol):
    """Channels and messages. The sandbox stays authoritative for state.

    A chat target is a transport and optional mirror, never the source of
    truth -- otherwise the lists the client *must* receive (408/409, 618/828)
    would depend on whether the target happens to have a concept of membership
    (BRIEF.md 7.5).
    """

    #: What the far side can actually do. Where a target lacks a concept --
    #: an ActivityPub timeline has no membership -- the sandbox synthesises it
    #: from its own state rather than degrading the protocol.
    capabilities: frozenset[str]

    def bind_chat(self, bridge: "ChatBridge") -> None:
        """Receive the inbound handle. Called once, before any traffic.

        Without this an adapter is outbound-only: it can push Napster chat into
        IRC but nothing can come back, which is half a bridge.
        """

    # outbound: the Napster client did something
    def on_join(self, session: Session, channel: str) -> None: ...
    def on_part(self, session: Session, channel: str) -> None: ...
    def on_public(self, session: Session, channel: str, text: str) -> None: ...
    def on_emote(self, session: Session, channel: str, text: str) -> None: ...

    def on_private(self, session: Session, to: str, text: str) -> bool:
        """A private message. Return True if the adapter delivered it.

        The sandbox calls this when the recipient is **not** a local session,
        so a Napster user can message someone who exists only on IRC.
        """

Those are the outbound hooks. For traffic coming the other way the adapter is handed a bridge at bind time, and deals in nicks, channels and text. It never formats a wire message:

napster.chat.irc . IrcChat.bind_chat
def bind_chat(self, bridge: "ChatBridge") -> None:
    self.bridge = bridge
    if not self.advertise:
        return
    # Make the offer visible where the client already looks. The channel
    # list is a window in the client; a channel that exists with a topic
    # is an invitation that needs no documentation.
    bridge.ensure_channel(
        self.console_channel,
        "nim's IRC console -- type: help")
    for entry in self.catalog:
        bridge.ensure_channel(entry.channel,
                              f"{entry.note} [{entry.network}]")
napster.chat.irc . IrcChat.on_public
def on_public(self, session: Session, channel: str, text: str) -> None:
    if channel == self.console_channel:
        self._run_console(session.nick, text, private=False)
        return
    where = self._resolve(channel)
    if not where.bridged:
        return
    conn = self._conns.get((where.network, session.nick))
    if conn is None:
        self._spawn(self._say_later(where, session.nick, text))
        return
    conn.privmsg(where.channel, text)

A user who exists only on the far side is registered through the bridge as a session with no socket. NIM stays the authority on who is in a channel, because the client asks for that list whether or not the far side has a concept of it. That is what makes a protocol with different semantics, Matrix or XMPP, a matter of writing the same two directions again rather than changing NIM.



Search and users

There is no network to search. NIM indexes a directory you point it at and answers searches from it, attributing each file to someone who does not exist.

Attribution happens when a file is indexed, not when it is found. A file keeps its owner, so the same track is always offered by the same person and browsing their library shows a coherent set. Owners cluster by directory, because a real shared folder is a collection rather than a sample:

napster.providers.collection . LocalCollection._owner_for
def _owner_for(self, path: Path) -> Persona:
    folder = path.parent
    held = self._owner_of_dir.get(folder)
    if held is not None and self._rng.random() > self.spread:
        self._by_nick_persona.setdefault(held.nick, held)
        return held
    person = self.people.make()
    self._by_nick_persona[person.nick] = person
    self._owner_of_dir.setdefault(folder, person)
    return person

Seventeen of the names are not invented. They are read off the one surviving screenshot of the client in use, and are handed out before anything is generated:

Generated names follow the shapes those seventeen exhibit, rather than a modern idea of a username. Word plus digits, two words joined, a compound noun, initials and a surname, or a keyboard mash:

    ("mash", _mash, 10),

What a search returns is a row per file. The address is explicit rather than taken from a socket, because these people have no sockets: their files are served by this machine.

napster.providers . Hit
@dataclass(frozen=True, slots=True)
class Hit:
    """One search result, before the sandbox turns it into a 201.

    ``ip`` and ``port`` are **explicit**, not substituted from the socket: a
    real server fills them from the session registry, a sandbox fills them with
    whatever its local peer endpoint is. One type serves both.
    """

    filename: str
    checksum: str
    size: int
    bitrate: int
    frequency: int
    seconds: int
    nick: str
    ip: int
    link_type: int = 0
    weight: int | None = None

Nothing here invents files. The collection is whatever it is, and a search with no match returns nothing.
