Where the client goes

NIM does not ship the Napster client and never installs one. You supply your own copy of the original, and where it goes depends on which mode you run.

A Wine prefix, for nim-byo. Install the client with its own installer, into a prefix of its own. The mode looks in ~/.local/share/nim/wineprefix unless --prefix or $WINEPREFIX says otherwise:

export WINEPREFIX=~/.local/share/nim/wineprefix
wineboot --init                 # once, to create the prefix
wine /path/to/setup.exe         # the installer you supplied
nim-byo                         # finds napster.exe in there

It lands at drive_c/Program Files (x86)/Napster/napster.exe, and the mode prints the path it found so you can see it picked the right one. A prefix per client keeps one install from disturbing another.

A Windows VM, for nim-vm. Install the client inside the guest, the way you would install anything there. Nothing on this side needs a copy, and nothing here can reach into the guest -- the mode writes a nim.reg for you to apply in it instead.

The sealed museum mode uses the prefix the project builds at ~/.local/share/nim/wineprefix. That is the same default nim-byo uses, so a prefix built for one works for the other.

Where the music goes. A folder of its own, ~/.local/share/nim/collection, made on first run with a README in it. Put music there and a mode offers it as search results, attributed to invented people. It is read and never written to.

It is deliberately not where the client writes downloads: the client puts those inside its own prefix, under C:\DOWNLOAD\MP3. A folder that was both would offer you your own downloads back as somebody else's files.

At the modem rate a four-megabyte MP3 takes about fifteen minutes to download, which is accurate. --latency broadband is a minute, and --latency none is instant.

If the mode says it cannot find a client, it is looking for napster.exe under drive_c in the prefix you gave it. Pass --prefix at the right one, or start the client yourself and leave the mode serving with --no-launch.



Running a mode

A mode installs as its own tool and runs from any directory. Pick the one that matches where your client is:

nim-byo — A client you installed yourself, in your own Wine prefix. Configures it in place and starts it. Redirects the client; does not confine it.

uv tool install --find-links nim/dist ./nim/modes/byo-wine
nim-byo --help
uv tool uninstall nim-mode-byo-wine

nim-vm — A client in a Windows VM, or on real hardware. Writes a .reg to apply in the guest. With a host-only adapter the guest's only route anywhere is this machine, which is the stronger seal of the two.

uv tool install --find-links nim/dist ./nim/modes/vm-guest
nim-vm --help
uv tool uninstall nim-mode-vm-guest

--find-links is only needed until the sandbox itself is published: it tells uv where to find the one dependency a mode has, built by uv build in nim/library.

Every mode takes --collection DIR to offer a real music folder as search results, --chat internal to keep chat out of IRC, and --latency to set the sign-in pace (modem, broadband, none, or a number). The first run pre-fetches the exhibits, which takes a few minutes and happens once.

Every mode also takes a backend. Search results, accounts, presence and the rest are capability domains, and a backend is a package that fills one or more of them. Install it alongside the mode and name it:

uv tool install --find-links nim/dist ./nim/modes/byo-wine --with my-napster-backend
nim-byo --backend my-backend      # one bundle, several domains
nim-byo --library my-shelf        # one domain, over the bundle's choice

The per-domain flags are --library, --identity, --presence, --rendezvous, --policy, --mail and --federation, each overriding whatever --backend chose. A name that is not installed is a startup error that says so.

Sign in as the account the mode configured, preserve unless you passed --nick. The client keeps its proxy settings per account, so any other name dials server.napster.com and fails.

If something goes wrong, run it again with --capture FILE. That writes a decoded transcript of the wire: one line per protocol message in each direction, and the handshake in front of each transfer. It is what to attach to a problem report, and it is the artefact the project's own findings were read out of. Read it before sending it on — it holds the nick, the password, every search term and every filename of that session, which is why it is off unless asked for.

There is a third mode, and it is not installable. The museum mode runs the client in a user namespace with no route out, asserted on every run, and it is how the sandbox is verified against a real client — the captures the notes are built on came from it. It stays a script in the repository, nim/harness/run-museum.sh, because it needs that namespace, a bind-mounted hosts file and two socket relays, so it is run from a checkout rather than installed. CHAT, LATENCY, NIM_COLLECTION and WINEPREFIX are its knobs.
